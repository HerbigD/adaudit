## 2. AuditCard 层级双样式（`04-parent-style-and-web-evidence.png`）

样本用 ConflictBrand（`leaf=0.55 / parent=0.86` → 粒度自适应降级到父类），
在复核页左右并列，一屏同时看到两种形态：

**左（original·初判，parent 态）**
```
大类 · 已确定    3. Dairy and alternatives      86%   ← 实心绿条
┌ 虚线框 ─────────────────────────────────┐
│ 细类 · 待定    —                          55%   ← 值位显示 "—"
│ 候选：[5] vs [19] —— 需营养证据裁定          │
└────────────────────────────────────────┘
```

**右（prediction·重裁决，leaf 态）**
```
大类            3. Dairy and alternatives      86%
细类            [19]                           55%   ← 无虚线框，实心
```

确定层级 = 实心 + 绿条；待定层级 = 虚线框 + 降透明度 + 值位 `—` + 候选码。

⚠️ **与任务书措辞的出入**：任务书示例是 `待定 · 候选 [2, 12]`，实现渲染为两行 ——
`细类 · 待定` 和 `候选：[5] vs [19] —— 需营养证据裁定`。**候选码本身是展示了的**，
只是排版拆成两行、分隔符用 `vs` 而非逗号。按"不扩大 scope"未改；要统一成任务书写法说一声，一行的事。

## 3. EvidenceList（`04` `05` `06` `07` `08`）

四种形态都拿到了实拍：

| 形态 | 徽标 | 证据 |
|---|---|---|
| web 联网证据 | `电商页面` / `其他`（灰） | `04` |
| 缓存 · auto | `缓存档案` + **`未经人工核验`（黄）** | `07` |
| 缓存 · human_verified | `缓存档案` + **`人工核验`（绿）** | `08` |
| 降级证据 | `降级证据 · 无营养面板`（黄） | `06` `07` |

**`normalized=null` 的呈现**（`05`）：ServingBrand 的页面只有 per-serving 读数且缺份量，
渲染为

```
糖 9g/serving · 未换算    脂肪 1.5g/serving · 未换算
纤维 2g/serving · 未换算   钠 120mg/serving · 未换算
```

原值照录、单位照录、明确标"未换算"（`title` 属性是"缺份量信息，无法换算"）。
对照 `04` 里可换算的读数是加粗的 `糖 18.7g/100`，两者一眼可分。

**构造 auto / human_verified 两条缓存证据的方法**（可复现）：
往 `product_cache` 播两条**只有 URL、没有营养读数**的档案（一条 `auto`、一条 `human_verified`），
再上传对应产品。命中缓存 → 无结构化读数 → 规则裁决置信度 0.60 上不去 → 落人工队列，
两种 provenance 的配色因此都能在复核页拍到。

## 附带发现（未修，留给后续决策）

**缓存命中存在同品牌近名误命中的风险。** 本次实测：上传 `Mock Crunchy Cereal 500g`，
命中了档案 `Mock Cereal 500g`，得分 **0.92 ≥ 0.82 阈值** —— 两者其实是不同产品。

拆开看：品牌精确匹配 0.55 + 名称 token 重叠 0.20×0.75 + 语义 0.25×高相似 ≈ 0.92。
问题在于**名称差异只占 20% 权重**，而"多一个修饰词"恰恰是快消品区分变体的主要方式。

放到真实数据上这是要出事的：`Amul Toned Milk` vs `Amul Double Toned Milk` ——
它们正好是 **5 vs 19**，是 eval 三大混淆对之一。缓存误命中会让系统**跳过搜索直接拿错档案裁决**，
而且因为走的是缓存路径，`search_status="cache"`，连"证据不足"的信号都不会有。

不属于今日四项，未动。可选处置（择一即可）：

1. 提高 `CACHE_HIT_THRESHOLD`（0.82 → 0.90），最省事，但会压低命中率
2. 名称 token 重叠改为**非对称**：档案名的 token 必须被查询名**全覆盖**才算命中
   （`Mock Cereal` ⊄ `Mock Crunchy Cereal` 的反向不成立 → 拒绝）
3. 命中后加一道"份量/规格一致"校验（`500g` vs `375g` 直接否决）

我倾向第 2 条：它针对的正是"多一个修饰词就是另一个产品"这个真实分布，且不牺牲整体命中率。
